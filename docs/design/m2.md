# M2 — Smarter gathering and crafting: rotation engine, scheduler, HQ intermediates, materia

Four parallel packages on top of M1 (docs/design/m1.md, docs/design/orders.md).
Merge order: P1 (rotation engine) first — P2 reads its cost table; then P3,
P4, P2. The coordinator wires new panels into `MainWindow` / `SettingsPanel`
and the one-line runner changes listed under "coordinator" below.

## P1 — Gathering rotation engine (7.14) — owns new `Core/Gathering/*` (except NodeKind.cs, which it may extend), `Core/GatheringActions.cs`, `Gathering/GatheringController.cs`, `Gathering/GatheringLoop.cs`, `Game/GatheringStateReader.cs`, `Game/DalamudGameBridge.cs` **only** for new gathering members (boon chance / bonus conditions / player statuses / item cooldowns), `Game/IGameBridge.cs` for those members (add at the end of the interface), new `Windows/GatheringRotationPanel.cs`, `CielCraft.Tests/GatheringRotationTests.cs`

1. **Action catalogue.** Replace the hard-coded ids in `GatheringActions`
   with a Core enum `GatherAction` (YieldI, YieldII, RestoreIntegrity,
   BountifulYield, GiftI, GiftII, Tidings, TwelvesBounty, GivingLand,
   WiseToTheWorld, Luck, Scour, Brazen, Meticulous, Scrutiny,
   CollectorsFocus / HighStandard / PrimingTouch as the game has them,
   Collect) and a plugin-side `GatheringActionCatalog` that resolves
   (action, job) → id from the `Action` sheet by English name at load (log
   what could not be resolved once; such actions are simply never chosen).
   Keep the two existing helpers' behaviour for MIN/BTN pairs. Cordials: the
   catalogue also lists the cordial items (Hi-Cordial, Cordial, Watered
   Cordial, NQ/HQ) with their GP value and cooldown group.
2. **Rotation tables (Core, testable).** `GatheringRotationTable` parsed
   from a small text format, one rule per line, evaluated top-down each
   time the controller may act at the node:
   `when <condition>[, <condition>...]: <action>` with conditions over
   `gp >= N`, `gp < N`, `integrity <= N`, `integrity == max`, `remaining > N`
   (items still needed), `remaining > integrity*yield`, `boon < N` (boon
   chance %), `bonus:boon` / `bonus:yield` / `bonus:attempts` (the node's
   unspoiled bonus condition of that type is present and not yet met),
   `status:eureka` (Eureka Moment), `used:<action>` / `!used:<action>`
   (already used this node), `kind:crystal`, `collectability < N`,
   `collectability >= goal`, `lastAttempt`. Built-in tables per node class
   (`NodeClass`: Normal, Unspoiled (also Legendary), Crystal, Collectable,
   Ephemeral = Collectable) with sensible defaults: yield buffs by GP
   threshold (Yield II at 500, Yield I at 400), Bountiful Yield each swing
   when GP allows and remaining > yield, Gift I/II + Tidings on unspoiled
   nodes when boon < 100 or a boon bonus is unmet, Solid Reason / Ageless
   Words while it pays (the existing rule), Eureka Moment → Wise to the
   World, Twelve's Bounty + Giving Land on crystal nodes, and the collectable
   loop Scrutiny → Meticulous (Scour when Scrutiny is unaffordable), Collect
   at goal or on the last attempt at the minimum (the existing rule).
   `GatheringRotationOverrides[className]` replaces a built-in table when it
   parses; a parse error is logged once and the built-in table is used.
   `GatheringRotationCost.GpPerNode` returns the table's cost for a full run
   (sum of the once-per-node buffs the top rules would fire at full GP).
3. **Node facts the engine needs, read by the plugin.** Boon chance and the
   node's bonus conditions: read `GatheringPointBonus` (via the
   `GatheringPoint` of the open node — the object's data id, or the location
   the runner passed) for the condition (type, value) and bonus (type,
   value); boon chance from `AddonGathering` if the installed ClientStructs
   exposes it, else from the window's text (`ReadAddonStrings`), else -1
   (unknown → the boon rules are skipped). Eureka Moment from the player
   status list. Item cooldowns for cordials
   (`ActionManager.GetRecastTime` / `IsRecastTimerActive` for item ids, or
   the item's action). Add these to `IGameBridge` (`GetGatheringNodeFacts()`
   returning a small record; `GetStatusRemainingSeconds(statusId)` may be
   made public; `IsItemOnCooldown(itemId)`).
4. **Controller / loop.** The controller's `TickBuffs` and `TickCollectable`
   ask the table what to do next (one action per decision, confirmed by the
   observed GP / integrity / collectability change as today; the "buff did
   not resolve → stop spending GP this node" safety stays). The loop's
   cordial logic becomes cordial-type aware: pick the strongest cordial
   whose GP fits (Hi 400 / 350 HQ… read the values from the item's
   `ItemFood`-like data or hard-code the three with a comment), never at the
   node, honour the cooldown, and drink when the next node's
   `GpPerNode` is not covered by current GP + regen during the walk.
   Keep every settle delay.
5. **Settings UI** (`GatheringRotationPanel.DrawSettings(Configuration)`,
   the coordinator calls it from Settings › Gathering): one collapsible
   block per node class showing the built-in table read-only, an override
   text box with parse feedback, Save / Clear.

## P2 — Timed-node scheduler (7.15) — owns new `Core/Scheduling/*`, `Crafting/ProductionRunner.cs`, `Game/GatheringDatabase.cs` (node kind refinement, crystal spots), new `Windows/SchedulePanel.cs`, `CielCraft.Tests/NodeSchedulerTests.cs`

1. **Schedule (Core, testable).** `NodeScheduler.Build(tasks, now, player
   GP / max GP / regen per tick, cordials owned, horizon)` where a task is
   (item, amount, windows, kind, territory, area, collectable) → a
   `Schedule` of `ScheduledVisit`s: for each timed task its next windows
   within the horizon (real start / end, ET hh:mm), how many nodes a window
   allows (window length ÷ per-node time ≈ 40 s + walk) and how many the GP
   allows (GP at arrival + regen + cordials ÷ `GatheringRotationCost`), the
   expected yield per visit (≈ integrity × (1 + yield buff) ×
   nodes-per-visit, conservative), so the number of windows an amount needs;
   the travel lead (teleport + travel: 2 real minutes today; make it a
   constant the runner passes); and the plan order: untimed tasks and
   ready craft steps between windows, timed tasks at their window. Gaps
   shorter than `WaitAtHomeMinutes` idle in place; longer ones go home when
   `WaitAtHomeForWindows` and a home is set (`CraftingLocation != Stay`).
2. **Runner.** `BuildGatherQueue` and the gather ordering use the schedule
   instead of "timed last, soonest first": a timed window opening within
   the lead goes first; while waiting for a window the runner does untimed
   gather tasks, then craft steps whose ingredients are already in the bag
   (a step is "ready" when `GetRecipeRequirements` covers `Crafts`), then
   goes home (`TeleportHome`, reuse the 7.6 phase) or idles; travel to the
   node starts `lead` before the window and the node loop starts the
   moment the window opens (it already tolerates "no node yet" for 45 s —
   raise that to the window's start + 1 min for timed tasks). A window
   that closes mid-run with the amount short re-schedules the next window
   (do not fail). `StatusText` says which window is being waited for and
   where. Keep `finishAfterReturn`, home teleport and stop-gently intact.
3. **Aetherial reduction for crystal clusters.** `GatheringDatabase` learns
   which ephemeral collectables reduce to which crystals/clusters
   (`Item` sheet: `AetherialReduce` flag + the reduction result table if
   Lumina has it; otherwise a bundled map for the elemental clusters with a
   comment). A plan whose raw material is a cluster (item ids of the
   elemental clusters) or a crystal with no normal node picks an ephemeral
   source: gather the collectable (the collectable path of the loop, tier
   High), then reduce (general action "Aetherial Reduction", the
   `PurifyItemSelector` / `PurifyResult` addons — read names via the
   reflect project, drive them with `FireAddonCallbackInt` /
   `ReadAddonStrings` the way repair is driven), verify the crystal count.
   Per-element crystal spot preference: `Configuration` may keep
   `CrystalSpots` (element → territory) — add it to `AutomationSettings`
   only if needed and say so. If reduction proves too large, deliver the
   scheduler fully and leave reduction as a clearly marked stub with a
   design note in your report.
4. **Schedule page** (`SchedulePanel.Draw()`; the coordinator wires it to
   Status › Schedule replacing the placeholder): a table of the timed items
   of the plan in flight (or the last preview: reuse `PlanTreePanel.Show`'s
   plan — add a static `SchedulePanel.Show(ProductionPlan?)` the same way),
   next window (ET and real countdown), expected nodes / yield per visit,
   windows needed, GP wanted, the runner's current wait (where, how long),
   and `DrawSettings(Configuration)` for the two wait-at-home fields.

## P3 — HQ-aware intermediates (7.22) — owns new `Core/Crafting/InitialQuality.cs` (formula + HQ mix), `Core/DependencyResolver.cs` (`HqCrafts`), `Core/Orders/OrderPlanner.cs` if the plan needs the seed step, `Crafting/BatchCrafter.cs`, `Crafting/SolverService.cs` (a detached / synchronous solve helper), `Game/DalamudRecipeProvider.cs` (`RecipeInfo` material data), `Core/Planning/PlanTree.cs` + `Windows/PlanTreePanel.cs` (show "N HQ" on a step), `CielCraft.Tests/InitialQualityTests.cs`

1. **Formula.** `RecipeInfo` gains `MaterialQualityFactor` and per
   ingredient `ItemLevel` + `CanBeHq` (crystals cannot). Initial quality
   for a HQ mix = floor(MaxQuality × MaterialQualityFactor / 100 ×
   Σ(HQ count × ilvl) / Σ(count × ilvl over HQ-able ingredients)); write
   the formula in one place with a comment saying it is validated in game
   (the coordinator does that) and expose `InitialQuality.For(recipe,
   maxQuality, hqCounts)` and `InitialQuality.MixFor(recipe, maxQuality,
   needed)` = the cheapest HQ counts (fewest HQ items, preferring the
   ingredient with the highest ilvl per item, whole crafts of the
   intermediate) reaching `needed`.
2. **Reachable from zero?** For a target step whose mode wants quality
   (Any with `TargetQualityPercent`, ForceHq, Collectable): solve the final
   recipe once at initial quality 0 with the character's stats
   (`SolverService` — add `SolveDetachedSync(setup, objective, timeout)` or
   reuse the craft test's detached instance; it may take seconds, so run it
   off the framework thread and let the plan wait — the `OrderRunner` /
   `ProductionRunner` start already has a Preparing phase; put the wait
   there and say where), replay it with `RotationSimulator.Run` to get the
   reachable quality; if it is short of the target, `MixFor` gives the HQ
   counts, re-solve at that initial quality to confirm, and set `HqCrafts`
   on the intermediate steps that produce those ingredients (an ingredient
   that is gathered / bought cannot be seeded — only crafted intermediates
   count; if no mix reaches the target, log it and keep quick). Cache the
   answer per (recipe, stats, target) in memory for the session.
3. **Batch.** `BatchCrafter.Start(quantity, quickSynth, requireHq,
   targetQuality, hqFirst = 0)`: the first `hqFirst` crafts run as normal
   synthesis with HQ required at 100% quality, the rest as today (quick
   when asked). The runner (coordinator) passes `step.HqCrafts`. The final
   craft's HQ fill (`FillIngredients(preferHq)`) already consumes them; make
   sure the batch's `FillHqIngredients` does not fill *more* HQ than the
   plan seeded when `PreferHqMaterials` is off (when on, filling all owned
   HQ is fine).
4. **Visibility.** Plan tree node text "N HQ of M crafts", the report's
   Plan section, and the `[Production]` step log line say "k HQ first".
   Settings toggle `HqIntermediates` (the coordinator adds the UI).

## P4 — Spiritbond / materia extraction (7.2) — owns `Game/MaintenanceService.cs`, `Game/DalamudGameBridge.cs` **only** for new materia members, `Game/IGameBridge.cs` for those members (add at the end), new `Windows/SpiritbondPanel.cs`, `Crafting/OrderRunner.cs` **only** if spiritbond mode needs a hook (prefer not), `CielCraft.Tests/MaintenanceTests.cs` (a fake bridge is fine)

1. **Bridge.** `GetSpiritbondReadySlots()` (equipped slots at 100%:
   `InventoryItem.Spiritbond == 10000` in `EquippedItems`),
   `OpenMaterialize()` (general action "Materia Extraction" — resolve the
   id from the `GeneralAction` sheet by name), `ExtractMateria(slot)` on
   the `Materialize` addon (callback values: read what other open-source
   plugins use — Artisan fires `(2, slotIndex)`; verify the addon's
   AtkValues with the reflect project and say what you found),
   `ConfirmMaterializeDialog()` (`MaterializeDialog` yes), `IsMaterializing`
   (the extraction animation / condition), `CloseMaterialize()`.
2. **Maintenance.** New phases Extracting → Confirming → WaitingForExtract
   → ClosingMaterialize between repair and consumables, gated by
   `AutoExtractMateria`, one piece per pass, verified by the slot's
   spiritbond dropping; the same timeouts / `BlockedReason` pattern as
   repair (a failure is non-fatal: log, disable for the session). Runs
   wherever `Tick` already runs (between crafts and between nodes). Count
   `MateriaExtracted` for the session and the report (`Describe`).
3. **Spiritbond mode** (`SpiritbondPanel.Draw()`, Tools › Spiritbond, the
   coordinator wires it): pick a cheap recipe (search like the craft test)
   or a gather item (search like the orders panel), a target materia count,
   Start / Stop. Running = a `BatchCrafter.Start(large)` loop or the
   `GatheringLoop` with the plugin's normal machines, stopped by the panel
   when `MateriaExtracted` reaches the target or the user presses Stop;
   show the equipped pieces' spiritbond % live. The `AutoExtractMateria`
   toggle: `SpiritbondPanel.DrawSettings(Configuration)` for Settings ›
   Crafting (coordinator wires it).
