Five parallel packages on top of the orders model (docs/design/orders.md).
Merge order: P1 (layout) last so it hosts everything; P2–P5 first.

  (`ConsumableSet { Food, Potion }` of `Consumable { ItemId, Hq }`),
  `CraftingLocation` (Stay / EstateHall / Apartment / InnRoom), `AssistMode`,
  `LockStep`, `ManualRotations` (recipe id → text). The legacy

  a positive `targetQuality` (a collectable tier threshold) replaces the

  before a craft step (Crafting) and before a gather task (Gathering); today
  it only records `Activity`.

  `Windows/RotationPanel.cs`, `Windows/CraftTestPanel.cs`,
  `Windows/ConsumablesPanel.cs` — each `new X(plugin)` + `Draw()`.

## P2 — Gather orders, collectables, home (7.1, 7.23, 7.6) — owns `Core/Orders/OrderPlanner.cs`, `Core/DependencyResolver.cs` (gather targets only), `ProductionRunner.cs`, `GatheringLoop.cs`, `GatheringController.cs`, `GatheringDatabase.cs`, `DalamudRecipeProvider.cs` (collectable thresholds), `DalamudGameBridge.cs` (estate teleport), `OrdersPanel.cs` (Kind / tier controls), tests for the planner
1. **7.1 Gather orders.** `Order.Kind == Gather`: the planner accepts an item
   the gathering database knows (`GetGatheringJob != null`) and emits it as a
   raw material of the plan with no craft step (add
   `Func<uint, bool> isGatherable` to `OrderPlanner.PlanGroup`; the runner
   already completes gather-only plans). Restock applies. The OrdersPanel
   gets a Kind combo (Craft / Gather) and the search box also finds
   gatherable items when Gather is selected (add a `SearchGatherable` on
   `GatheringDatabase` over the item sheet + node data). Collectable
   gathering: with `Mode == Collectable` on a gather order the loop counts
   collectables taken (the controller already appraises) toward the amount
   and targets the tier's collectability; wire the tier through
   `GatheringLoop.Start`.
2. **7.23 Collectable crafting.** A craft order with `Mode == Collectable`
   is accepted when the recipe is a collectable (`RecipeInfo.RequiredQuality
   > 0` or the item is in the CollectablesShop sheets — add
   `GetCollectableThresholds(itemId) → (Low, Mid, High)?` on the recipe
   provider from `CollectablesShopItem` / `CollectablesShopRefine`; if the
   sheets are awkward, the recipe's RequiredQuality is the low tier and the
   others scale as the game does — say which you used). The runner passes
   `targetQuality` = the tier threshold to `BatchCrafter.Start`; the batch
   verifies by item count as today; the summary reports the count and the
   quality the solve targeted. `OrderPlanner.Evaluate` stops refusing
   Collectable; the OrdersPanel shows the tier combo when the mode is
   Collectable.
3. **7.6 Home teleport.** `CraftingLocation` other than Stay: before the
   first craft step (after gathering, instead of the zone-aetheryte
   return), teleport to the estate hall / apartment / inn. Implement
   `IGameBridge.TeleportHome(CraftingLocation)` on the Dalamud bridge with
   Telepo and the aetheryte list's estate / apartment entries (the entries
   with `IsSharedHouse` / `Plot` / `IsApartment` flags; inn = the "Return"
   or nearest city aetheryte + the inn is out of scope for Telepo — if the
   inn cannot be reached by teleport, log and fall back to Stay and say so
   in the report). Wait for the loading screen the way the return teleport
   does; fall back to crafting in place with a log line when no home
   aetheryte exists.

call later; document it). `PlanText` renders the same tree as indented text
for `/cielcraft plan` and a "Plan" section of the diagnostic report.

## P4 — Rotations, craft test, assist, lock-step (7.8, 7.18) — owns new `Core/Rotations/RotationText.cs`, `Windows/RotationPanel.cs`, `Windows/CraftTestPanel.cs`, `Crafting/BatchCrafter.cs`, `Crafting/CraftAutomator.cs`, `Crafting/SolverService.cs`, `Core/RaphaelActionNames.cs`, `CielCraft.Tests/RotationTextTests.cs`
1. `RotationText.Parse(string) → (IReadOnlyList<uint> ActionIds, IReadOnlyList<string> Errors)`
   accepting action names one per line or comma-separated and Teamcraft
   macro lines (`/ac "Basic Synthesis" <wait.3>`, `/action`), names matched
   case-insensitively against `RaphaelActionNames` (add a reverse lookup
   there); `Format(IReadOnlyList<uint>)` back to names.
2. Manual rotations: when `ManualRotations` has the recipe id, `BatchCrafter`
   skips the solve and runs that rotation with the same adaptive recovery
   (the mid-craft re-solve still uses Raphael); the log says "manual
   rotation". The RotationPanel has an editor per selected recipe (the
   crafting-log selection or the in-flight recipe): text box, Parse
   feedback, Save / Clear.
3. RotationPanel view: the active rotation (solved or manual) as a list with
   executed / current / pending marks, the executor state, and the solve's
   expected result (`CraftSolution` base progress/quality and the solver's
   reported final numbers if available — extend `CraftSolution` only if the
   native result carries them; otherwise show what exists and say so).
4. Assist mode: in `BatchCrafter.OnTick` while Idle, if `AssistMode` and the
   game is crafting on step 1 with no batch running, `Start(1)` (attach) and
   log "assist". Lock-step: in `CraftAutomator`, when `LockStep` is on, pause
   before each action with reason "lock-step"; a `Step()` method executes
   exactly one action and pauses again; the RotationPanel shows Step /
   Continue buttons; `/cielcraft step` is wired by the coordinator later —
   expose `CraftAutomator.Step()` and `plugin.CraftAutomator` already exists.
5. Craft test (CraftTestPanel): pick a recipe (search), stats default to the
   character's (editable craftsmanship / control / CP / level), Solve →
   rotation + expected progress / quality / HQ % (quality / max quality
   mapped through the game's HQ chance table — include the table) and solve
   time; uses `SolverService.BeginSolve` on a separate `SolverService`
   instance or a new `SolveDetached(setup, objective, callback)` so it
   never disturbs a running batch.
